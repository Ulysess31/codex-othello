## 검증 기록

### 2026-10-09 GitHub Pages 배포 설정

- `git ls-remote origin HEAD` — **실패: 네트워크 접근 차단으로 github.com:443 연결 실패.** 원격 브랜치 상태와 기존 Pages 설정을 조회할 수 없다.
- `npm run build` — 첫 실행은 sandbox의 `spawn EPERM` 오류로 실패했다. 권한이 있는 재실행은 **통과**했으며 `dist/index.html`의 JS/CSS 경로가 `/codex-othello/assets/...`로 생성되는 것을 확인했다.
- `git diff --check` — **통과.** Git 줄바꿈 안내만 있었고 공백 오류는 없다.
- `curl.exe -I https://ulysess31.github.io/codex-othello/` — **HTTP 404.** 최초 설정 push 뒤에는 실제 Pages 사이트가 열리지 않았다.
- 공식 Pages 설정 확인 단계(`actions/configure-pages@v5`)를 workflow에 추가해 `main`에 push했다. Actions 로그에서 Pages 사이트가 없는 오류를 확인했다.
- `gh repo view` — 저장소가 비공개이고 현재 계정이 관리자임을 확인했다.
- `gh api --method POST repos/Ulysess31/codex-othello/pages -f build_type=workflow` — **실패, HTTP 422.** 현재 요금제는 비공개 저장소의 Pages 생성을 지원하지 않는다.
- 사용자 승인 뒤 `gh repo edit ... --visibility public`으로 저장소를 공개하고 Pages API로 `build_type=workflow`를 설정했다.
- `gh run rerun 37898415100` — **성공.** Pages 설정, 빌드, artifact 업로드, 배포 작업이 모두 통과했다. GitHub에서 Node.js 20 지원 종료 예정과 Ubuntu 이미지 이전 안내를 경고로 표시했다.
- `curl.exe`로 `https://ulysess31.github.io/codex-othello/` 요청 — **HTTP 200.** 반환 HTML의 제목이 `오델로`이고 JavaScript·CSS 경로가 저장소 하위 경로를 포함하는 것을 확인했다.
- 이 작업에서는 lint와 테스트를 실행하지 않았다. 사이트가 브라우저에서 실제로 게임 조작되는지는 별도 수작업 확인하지 않았다.

## GitHub에서 직접 배포 설정하고 확인하기

이 저장소는 이미 GitHub Pages가 준비돼 있으며, 배포 주소는 <https://ulysess31.github.io/codex-othello/>다. GitHub 화면에서 설정이나 실행 결과를 확인하려면 다음 순서로 이동한다.

1. GitHub에서 <https://github.com/Ulysess31/codex-othello> 저장소를 연다.
2. 저장소 위쪽의 **Settings**를 누르고 왼쪽 메뉴에서 **Pages**를 연다. **Build and deployment**의 **Source**가 **GitHub Actions**인지 확인한다. 현재 이 값으로 설정돼 있다.
3. 저장소 위쪽의 **Actions** 탭을 열고 **Deploy to GitHub Pages** workflow를 선택한다. 마지막 실행을 누르면 빌드와 배포 작업이 초록색 체크로 끝났는지 확인할 수 있다.
4. 다시 실행하려면 workflow 화면의 **Run workflow**를 누르고 `main` 브랜치를 선택한 다음 실행 버튼을 누른다. 저장소 루트의 `.github/workflows/deploy.yml`이 실행 순서를 정한다.
5. 앞으로 `main` 브랜치에 변경을 push하면 workflow가 자동으로 실행된다. workflow는 `npm ci`로 도구를 준비하고 `npm run build`로 사이트 파일을 만든 뒤 `dist/` 폴더를 게시한다.
6. 실행 결과에서 **deploy** 작업까지 성공하면 위 Pages 주소를 새로고침한다. 첫 게시나 설정 변경 직후에는 사이트가 반영되기까지 잠시 기다려야 할 수 있다.

현재 저장소는 공개 상태다. 이 GitHub 계정의 요금제는 비공개 저장소의 Pages를 지원하지 않아 비공개로 되돌리면 게시할 수 없다. 저장소 공개 범위를 바꾸면 소스 코드와 Git 기록의 공개 여부도 함께 바뀐다.

## Vercel 배포 현황

- 배포 브랜치: `vercel-othello` (원격 `origin/vercel-othello`까지 push 완료)
- 임시 Vercel 배포: <https://temporary-speedy-spinel-tk2ys5s.vercel.app/>. CLI 로그아웃 상태에서 만든 익명 임시 주소이며 60분 후 만료된다.
- 페이지와 JS·CSS 파일은 모두 HTTP 200으로 응답했다. Vercel CLI 계정 연결은 되지 않아 이 임시 배포는 저장소 자동 배포 프로젝트와 연결되지 않았다.
- 계속 쓰려면 Vercel에 로그인해 임시 배포를 claim하거나, `vercel.md` 절차대로 GitHub 저장소를 가져와 `vercel-othello` 브랜치의 Preview 배포를 설정한다.

- 기반 프로젝트는 React 19.3.0, Vite 8.3.2, Vitest 5.0.3으로 설치됐다. 정확한 의존성 트리는 `package-lock.json`에 고정돼 있다.
- 현재 Vitest는 React 화면 테스트 1개, 오델로 규칙 테스트 14개, 키보드 좌표 이동 테스트 3개로 총 18개를 실행한다.

## 검증 기록

검증은 코드를 실행해 예상한 동작과 실제 결과가 같은지 확인하는 과정이다. 명령 이름만 적는 대신 아래 기록에는 **무엇을 확인했는지**와 **왜 확인하는지**를 함께 적는다. 각 단계의 검증은 그 단계 작업이 끝났을 때 실행한다. 아직 하지 않은 검증은 완료한 것처럼 적지 않는다.

### 2026-10-05 — 1단계 프로젝트 기반 구성

- `npm install` — **결과: 성공.** 프로젝트가 필요로 하는 개발 도구를 내려받아 설치했다. 설치 과정에서 패키지 157개를 감사했고 알려진 취약점이 0건이었다. 앱을 실행하고 검사하기 전에 필요한 준비 단계다.
- `npm run dev -- --host 127.0.0.1` — **결과: 서버 시작 성공.** Vite 개발 서버가 로컬 주소에서 실행됐다. 코드 변경을 브라우저에서 확인할 수 있는지 보기 위한 단계다.
- `http://127.0.0.1:5173/` 요청 — **결과: HTTP 200.** 개발 서버가 페이지 요청에 정상 응답하고 오델로 페이지 HTML을 반환했다. 서버가 켜졌다는 로그만으로 끝내지 않고 실제 페이지 요청도 되는지 확인했다.
- `npm run lint` — **결과: 통과.** ESLint가 현재 JavaScript/React 코드에서 설정된 문법·작성 규칙 위반을 찾지 못했다. 실행 전 잡을 수 있는 일부 실수를 일찍 발견하기 위한 검사다.
- `npm run test` — **결과: 통과, 테스트 파일 1개·테스트 1개.** `src/setup.test.jsx`가 기본 React 화면 렌더링, `<main>` 영역과 “오델로” 제목을 확인했다. 앱 뼈대가 화면을 만들 수 있는지 확인하기 위한 시작 테스트다. 게임 규칙을 확인한 것은 아니다.
- `npm run build` — **결과: 통과.** Vite가 브라우저 배포에 사용할 파일을 `dist/`에 만들었다. 개발 중에만 동작하는 코드가 아니라 배포용 파일도 만들어지는지 확인했다.
- Vite/Vitest는 제한된 sandbox에서 자식 프로세스 실행 시 `EPERM`이 발생해 테스트와 빌드를 권한 승인된 실행 환경에서 확인했다.
- 수동 브라우저 플레이, 오델로 규칙 검증은 아직 하지 않았다. 게임이 아직 구현되지 않아 2단계 이후에 진행한다.

- 보드에 들어온 뒤 방향키로 포커스를 옮기고, 가장자리에 도달하면 그 자리에서 멈추도록 했다. 키보드 사용자가 마우스 없이 칸을 고를 수 있게 하는 작업이다.
- Enter와 Space는 별도 키 입력 코드를 만들지 않고 HTML 버튼의 기본 선택 동작을 사용한다. 브라우저가 기본 제공하는 동작을 쓰면 코드가 단순하고 일관적이다.
- 각 버튼 이름에 좌표(A1~H8), 돌 상태, 놓을 수 있는지 여부를 넣고 보드 위에 키보드 사용 안내를 표시했다. 색과 점만 보지 않고도 칸의 의미를 알아볼 수 있다.
- `boardNavigation.js`를 추가해 방향키의 좌표 계산을 화면 표시와 분리했다. 키 입력에 따른 다음 칸 계산만 담당해 기능과 테스트 대상을 작게 나눈다.
- 기존 CSS 미디어 쿼리 레이아웃을 사용하고 보드 안내 영역을 추가했다. 새 화면 프레임워크 없이 작은 화면을 계속 관리한다.

**자동 검증 기록과 의미**

- `npm run test` — **통과, 테스트 파일 3개·테스트 18개.** 기존 오델로 규칙 14개와 화면 테스트 1개, 방향키 계산 테스트 3개가 통과했다. 네 방향과 보드 경계에서 이동 계산이 기대대로 되는지, 화면에 하나의 Tab 진입점과 칸 설명이 렌더링되는지 확인한다.
- `npm run lint` — **통과, 오류와 경고 없음.** React/JavaScript 작성 규칙을 확인한다.
- `npm run build` — **통과.** Vite가 20개 모듈을 변환해 `dist/`에 배포용 HTML·CSS·JavaScript를 생성했다. 개발 코드가 배포 파일로도 묶이는지 확인한다.
- Vitest와 Vite 빌드는 sandbox 자식 프로세스 `EPERM` 오류 때문에 권한 승인된 환경에서 재실행했고 통과했다.
- 조작 가능한 브라우저 연결 목록은 비어 있다. 자동 검사는 통과했지만 실제 DOM 포커스, Enter/Space 키 입력, 좁은 화면 가로 넘침은 이 세션에서 직접 확인하지 못했다.
- 따라서 4단계 코드와 자동 검증은 완료했고, 브라우저 수작업 확인을 기다린다. 자동 검사 결과와 사람이 직접 확인해야 하는 결과의 차이를 분명히 하기 위한 기록이다.

**사용자 브라우저 수작업 확인 방법 — 4단계**

1. 터미널에서 `npm run dev`를 실행하고 표시된 주소를 Chrome 또는 Edge에서 연다.
2. 페이지에서 Tab을 눌러 보드에 진입한다. 보드 칸 64개를 전부 순회하지 않고 한 칸에 포커스가 들어오는지 확인하고, 화면에 표시된 키보드 안내를 읽는다.
3. 방향키로 포커스 테두리가 한 칸씩 이동하는지 확인한다. 좌상단 A1에서 위쪽·왼쪽 키를 눌러도 보드 밖으로 이동하지 않는지 본다.
4. A1에서 아래 방향키를 두 번, 오른쪽 방향키를 세 번 눌러 D3으로 이동한 뒤 Enter를 누른다. 흑 돌이 D3에 놓이고 D4의 백 돌이 뒤집히며 점수가 흑 4·백 1이 되는지 확인한다. 새 게임을 시작한 뒤 같은 방식으로 D3을 선택하고 Space를 눌러도 같은지 확인할 수 있다.
5. 브라우저 폭을 넓은 화면(예: 1280px)과 좁은 모바일 화면(예: 375px)으로 바꾼다. 보드가 정사각형으로 유지되고 점수·안내가 잘리지 않으며 페이지 전체에 가로 스크롤이 생기지 않는지 확인한다.
6. 개발 서버를 종료할 때 실행 중인 터미널에서 `Ctrl+C`를 누른다.
