## 검증 기록

검증은 코드를 실행해 예상한 동작과 실제 결과가 같은지 확인하는 과정이다. 명령 이름만 적는 대신 아래 기록에는 **무엇을 확인했는지**와 **왜 확인하는지**를 함께 적는다. 각 단계의 검증은 그 단계 작업이 끝났을 때 실행한다. 아직 하지 않은 검증은 완료한 것처럼 적지 않는다.

### 2026-10-05 — 1단계 프로젝트 기반 구성

- `npm install` — **결과: 성공.** 프로젝트가 필요로 하는 개발 도구를 내려받아 설치했다. 설치 과정에서 패키지 157개를 감사했고 알려진 취약점이 0건이었다. 앱을 실행하고 검사하기 전에 필요한 준비 단계다.
- `npm run dev -- --host 127.0.0.1` — **결과: 서버 시작 성공.** Vite 개발 서버가 로컬 주소에서 실행됐다. 코드 변경을 브라우저에서 확인할 수 있는지 보기 위한 단계다.
- `http://127.0.0.1:5173/` 요청 — **결과: HTTP 200.** 개발 서버가 페이지 요청에 정상 응답하고 오델로 페이지 HTML을 반환했다. 서버가 켜졌다는 로그만으로 끝내지 않고 실제 페이지 요청도 되는지 확인했다.
- `npm run lint` — **결과: 통과.** ESLint가 현재 JavaScript/React 코드에서 설정된 문법·작성 규칙 위반을 찾지 못했다. 실행 전 잡을 수 있는 일부 실수를 일찍 발견하기 위한 검사다.
- `npm run test` — **결과: 통과, 테스트 파일 1개·테스트 1개.** `src/setup.test.jsx`가 기본 React 화면 렌더링, `<main>` 영역과 “오델로” 제목을 확인했다. 앱 뼈대가 화면을 만들 수 있는지 확인하기 위한 시작 테스트다. 게임 규칙을 확인한 것은 아니다.
- `npm run build` — **결과: 통과.** Vite가 브라우저 배포에 사용할 파일을 `dist/`에 만들었다. 개발 중에만 동작하는 코드가 아니라 배포용 파일도 만들어지는지 확인했다.
- Vite/Vitest는 제한된 sandbox에서 자식 프로세스 실행 시 `EPERM`이 발생해 테스트와 빌드를 권한 승인된 실행 환경에서 확인했다.
- 수동 브라우저 플레이, 오델로 규칙 검증은 아직 하지 않았다. 게임이 아직 구현되지 않아 2단계 이후에 진행한다.

### 2026-10-05 — 2단계 오델로 규칙 엔진

**이 단계에서 한 일과 이유**

- `src/game/othello.js`에 규칙 계산을 모았다. 화면 코드와 분리한 이유는 규칙 오류와 화면 표시 오류를 따로 찾을 수 있고, 게임 화면을 만들기 전에 오델로 규칙 자체를 확인할 수 있기 때문이다.
- `createInitialBoard`는 매 게임의 표준 시작 상태를 만든다. `getFlips`와 `getLegalMoves`는 어디에 둘 수 있고 어떤 돌이 뒤집히는지 판정한다.
- `applyMove`는 합법 수를 확인하고 새로운 보드 복사본에 착수와 뒤집기를 반영한다. 입력 보드를 바꾸지 않는 이유는 이전 React 상태가 의도치 않게 변하는 일을 막기 위해서다.
- `getNextTurn`은 방금 둔 플레이어를 입력받아 상대 차례, 자동 패스, 게임 종료를 결정한다. 양쪽 모두 둘 곳이 없으면 빈칸이 남아도 종료하며 점수로 승자를 정한다.
- `countDiscs`는 화면이 필요할 때 보드에 있는 흑과 백의 돌을 다시 세도록 한다. 점수를 별도 상태로 복사해 보드와 점수가 어긋나는 일을 피한다.
- `src/game/othello.test.js`에 규칙 테스트 14개를 추가했다. 예상 결과를 코드로 고정해 이후 화면 연결이나 리팩터링 중에도 핵심 규칙이 깨지지 않았는지 반복 확인할 수 있다.

### 2026-10-05 — 3단계 게임 화면과 규칙 연결

**이 단계에서 한 일과 이유**

- `src/App.jsx`가 게임 상태를 한곳에서 관리하고, 사용자가 고른 좌표를 규칙 함수에 전달하도록 했다. 보드·차례·점수를 한 화면 상태에서 갱신해 서로 다른 데이터가 섞이지 않게 한다.
- `src/components/Board.jsx`는 보드 64칸을 표시하고 좌표와 돌 상태를 버튼 이름으로 전달한다. 합법 수 표시는 규칙 함수가 계산한 결과를 받아 그리므로 화면 컴포넌트가 규칙을 다시 구현하지 않는다.
- `src/components/GameInfo.jsx`는 현재 차례, 점수, 안내, 승패와 새 게임 버튼을 표시한다. 화면 책임을 나눠 파일별 역할을 이해하기 쉽도록 했다.
- `src/styles/app.css`에 보드와 정보 영역의 기본 배치·색상을 넣고 작은 화면에서는 세로 배치로 바뀌도록 했다. 화면을 실제로 사용하고 좁혀 볼 수 있는 기반이다. 세부 키보드 접근성은 4단계에서 다룬다.
- `src/setup.test.jsx`를 초기 게임 화면 확인으로 바꿨다. 64칸, 시작 가능한 칸, 차례·점수, 새 게임 버튼이 화면에 빠지지 않았는지 자동 확인한다.

**자동 검증 기록과 의미**

- `npm run test` — **통과, 테스트 파일 2개·테스트 15개.** 규칙 테스트 14개와 초기 화면 테스트 1개가 통과했다. 시작 보드와 합법 수 표시가 실제 화면 결과에 나타나는지 확인한다. 버튼 클릭 동작 자체는 이 테스트에서 자동 조작하지 않는다.
- `npm run lint` — **통과.** 새 컴포넌트와 상태 연결 코드가 프로젝트의 JavaScript·React 작성 규칙에 맞는지 확인했다.
- `npm run build` — **통과.** React 화면과 스타일이 브라우저 배포용 파일로 변환되는지 확인했다.
- `npm run dev -- --host 127.0.0.1` — **서버 시작 성공.** 페이지와 `App.jsx`, `Board.jsx`, `GameInfo.jsx` 요청이 모두 HTTP 200이었다. 개발 서버가 새 모듈을 제공하는지 확인한 것이며 마우스 클릭을 확인한 것은 아니다.
- 이 세션에는 조작 가능한 브라우저 연결이 없어 클릭 기반 수작업 검증을 수행하지 못했다. 따라서 3단계는 사용자 수작업 확인을 기다리는 상태로 기록한다.

**사용자 수작업 테스트 방법**

1. 프로젝트 폴더의 터미널에서 `npm run dev`를 입력한다. Vite가 개발 서버를 켜면 표시된 로컬 주소(보통 `http://localhost:5173/`)를 연다.
2. 시작 화면에 8×8 보드가 보이고 흑 2개·백 2개, 흑 차례와 가능한 위치 네 곳(D3, C4, F5, E6)이 표시되는지 확인한다. 게임의 시작 상태가 규칙과 일치하는지 보는 단계다.
3. D3 칸을 선택한다. 흑 돌이 D3에 놓이고 그 아래 D4의 백 돌이 흑으로 뒤집혀야 한다. 점수는 흑 4, 백 1이 되고 차례는 백으로 바뀌어야 한다. 한 번의 사용자 입력이 보드·규칙 함수·화면 갱신을 통과하는지 확인한다.
4. A1처럼 표시되지 않은 칸을 선택한다. 돌 배치와 점수, 차례는 바뀌지 않고 둘 수 없다는 안내만 바뀌어야 한다. 잘못된 입력이 보드를 손상하지 않는지 확인한다.
5. 새 게임을 누르고 확인창에서 취소한다. 현재 판이 유지되어야 한다. 다시 누르고 확인하면 시작 배치와 흑 차례, 2 대 2 점수로 돌아가야 한다. 확인 선택이 초기화 동작에 올바르게 반영되는지 확인한다.
6. 서버를 종료하려면 개발 서버가 실행 중인 터미널에서 `Ctrl+C`를 누른다.

자동 테스트는 첫 화면과 규칙 계산을 확인하고, 위 수작업은 실제 클릭 이후의 연결 흐름을 확인한다. 패스와 게임 종료 규칙은 자동 규칙 테스트에서 검증했지만, 화면에 해당 안내가 표시되는지는 실제 한 판을 진행해 확인할 수 있다.
